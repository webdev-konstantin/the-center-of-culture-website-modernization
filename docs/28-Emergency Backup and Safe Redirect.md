# Что было сделано — простыми словами

Цель Дня 28 — подготовить сайт к ситуации, когда доступ к текущему хостингу может стать недоступен: сохранить всё необходимое для восстановления проекта и после проверки резервных копий безопасно перенаправить посетителей на действующий официальный ресурс.

Если бы эта цель была сформулирована в самом начале, оптимальная последовательность выглядела бы так:

```text
полный backup файлов
        ↓
контрольная распаковка архива
        ↓
полный экспорт MySQL
        ↓
проверка структуры и данных SQL
        ↓
сохранение параметров хостинга и SSL
        ↓
сохранение относящейся к услуге документации
        ↓
тестовый HTTP 302 redirect
        ↓
проверка конечного адреса
        ↓
постоянный HTTP 301 redirect
```

Главный результат: проект не просто сохранён «одним архивом». Получен проверенный комплект для восстановления — файлы сайта, база данных и техническая информация — а старый публичный адрес корректно перенаправляет посетителей на актуальный официальный ресурс.

# Главная задача дня

Нужно было одновременно решить две разные задачи:

- не потерять разработанный сайт и данные;
- не оставить посетителей на потенциально недоступном старом ресурсе.

Критически важен порядок: сначала резервирование и проверка, только потом изменение публичного поведения сайта.

---

# 1. Сохранена вся файловая часть сайта

Вместо копирования только новой разрабатываемой версии был заархивирован весь корневой каталог публичной части сайта.

Это сохраняет в одном комплекте:

- новую версию сайта;
- существующую публичную часть;
- PHP-компоненты;
- CSS и JavaScript;
- изображения и загрузки;
- служебные файлы;
- правила `.htaccess`;
- связанные каталоги и зависимости.

Для резервной копии использован формат `tar.gz`.

```text
корневой каталог сайта
        ↓
TAR-контейнер
        ↓
GZIP-сжатие
        ↓
единый backup .tar.gz
```

---

# 2. Архив не просто скачан — он проверен распаковкой

Сам факт наличия большого архивного файла ещё не гарантирует возможность восстановления.

Поэтому резервная копия была распакована локально в два этапа:

```text
.tar.gz
   ↓
.tar
   ↓
обычная папка сайта
```

После распаковки проверено наличие основных каталогов и файлов проекта, включая актуальную новую версию, административную часть, API, стили, изображения, общие PHP-компоненты, JavaScript, загрузки и языковую версию.

Это подтвердило, что архив содержит реальное дерево проекта, а не пустой или повреждённый контейнер.

---

# 3. Отдельно сохранена база данных

Файлового backup недостаточно: динамический сайт зависит от MySQL.

Поэтому вся используемая база была экспортирована целиком через phpMyAdmin в формат SQL.

В экспорт включены:

- структура таблиц;
- данные таблиц;
- `AUTO_INCREMENT`;
- команды создания объектов базы;
- данные в виде `INSERT`;
- кодировка UTF-8;
- дополнительные объекты базы, если они присутствуют.

Таким образом, резервная копия состоит из двух независимых частей:

```text
ФАЙЛЫ САЙТА       БАЗА ДАННЫХ
    │                  │
 .tar.gz             .sql
    │                  │
    └────────┬─────────┘
             ↓
      комплект восстановления
```

---

# 4. SQL-export проверен по содержимому

SQL-файл также не был принят «на веру» только по размеру.

Внутри проверено наличие двух ключевых типов команд:

```sql
CREATE TABLE ...
```

и

```sql
INSERT INTO ...
```

Первая подтверждает сохранение структуры базы, вторая — наличие самих данных.

Контрольная таблица содержала и описание полей, и реальные строки данных. Следовательно, экспорт включает не только пустую схему.

---

# 5. Сохранена техническая информация о текущем размещении

Дополнительно зафиксированы экраны с параметрами, которые могут понадобиться при последующем переносе или разборе старой конфигурации:

- информация о хостинге;
- технические параметры услуги;
- состояние SSL;
- относящаяся к услуге договорная и техническая документация.

При этом не создавалась лишняя копия всей справочной базы провайдера: сохранялись только материалы, имеющие практическое отношение к хостингу, SSL и технической поддержке.

---

# 6. DNS не изменялся без необходимости

Управление основной DNS-конфигурацией выполняется отдельно от текущего хостинга.

Поэтому в рамках Дня 28 DNS-зона не перестраивалась и почтовые записи не затрагивались.

Это важное архитектурное разделение:

```text
DNS → определяет, куда направляется домен

Web server → отвечает на HTTP/HTTPS-запрос

HTTP redirect → сообщает браузеру новый URL
```

Для задачи перенаправления посетителя требовался именно HTTP redirect, а не изменение DNS-записей.

---

# 7. Найден существующий корневой `.htaccess`

Перед изменением перенаправления был проверен уже существующий `.htaccess`.

Он содержал простое правило принудительного перехода с HTTP на HTTPS.

Это позволило не создавать второй конфликтующий механизм, а аккуратно изменить существующую точку управления поведением Apache.

---

# 8. Сначала внедрён временный 302 redirect

Постоянный `301` не использовался сразу.

Сначала был установлен временный redirect:

```apache
RewriteEngine On

RewriteRule ^ https://TARGET-URL/ [R=302,L]
```

`TARGET-URL` здесь — условное обозначение конечного официального адреса. Сам адрес в документации проекта намеренно не фиксируется.

Почему сначала `302`:

- можно безопасно проверить конечный URL;
- ошибка не превращается сразу в постоянное перенаправление;
- уменьшается риск нежелательного кэширования ошибочного результата;
- финальное решение принимается только после фактической проверки.

---

# 9. Тестовое перенаправление проверено в браузере

После сохранения `.htaccess` старый адрес был открыт отдельно и фактически перенаправил браузер на требуемый ресурс.

То есть была проверена вся цепочка:

```text
старый URL
   ↓
Apache
   ↓
.htaccess
   ↓
302
   ↓
правильный конечный URL
```

Только после этой проверки временный статус можно было заменить постоянным.

---

# 10. Включён постоянный 301 redirect

После успешного теста изменился только HTTP-статус:

```text
302 → 301
```

Финальная логика:

```apache
RewriteEngine On

RewriteRule ^ https://TARGET-URL/ [R=301,L]
```

Теперь запросы к старому сайту получают постоянное перенаправление на актуальный официальный ресурс.

При этом файлы и база старого проекта не удалялись.

---

# 11. Почему не создавался ещё один ZIP или RAR

После проверки `tar.gz` создание второго архива тех же файлов в ZIP/RAR не повышает надёжность существенно.

Полезнее разделять понятия:

```text
другой формат архива ≠ независимая резервная копия

другая физическая точка хранения = дополнительная защита
```

Поэтому оптимальная схема хранения выглядит так:

```text
распакованная рабочая копия
          +
исходный проверенный .tar.gz
          +
SQL-export
          +
техническая документация
          +
копия комплекта на независимом носителе/хранилище
```

Резервные копии с конфигурационными файлами и SQL не предназначены для публикации в открытом Git-репозитории.

# Что изменилось для администратора

Теперь существует понятный аварийный комплект восстановления.

Если потребуется перенос на другой сервер, базовая последовательность будет такой:

1. распаковать файловый архив;
2. создать новую MySQL-базу;
3. импортировать SQL;
4. указать новые параметры подключения;
5. настроить document root;
6. восстановить HTTPS;
7. проверить маршрутизацию и публичные страницы.

То есть проект больше не зависит от единственной работающей копии на одном хостинге.

# Что изменилось для посетителя

Посетителю не нужно знать о резервировании, переносе или серверной конфигурации.

При обращении к старому адресу он автоматически получает постоянное перенаправление на актуальный официальный ресурс.

Это и есть правильный пользовательский результат: технические изменения остаются незаметными.
