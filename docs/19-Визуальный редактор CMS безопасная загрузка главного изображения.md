# День 19 — Визуальный редактор CMS: безопасная загрузка главного изображения

**Дата:** 2026-08-06  
**Статус:** завершено  
**Оценка дня:** 5/5


# Что было сделано — простыми словами

В День 19 редактор публикаций научился работать с настоящими изображениями.

Раньше поле `image_path` уже существовало в базе данных, однако редактор не умел сам загружать файл на сервер. Нужно было заранее знать путь к изображению и вручную вставлять его в поле. Для обычного редактора сайта это неудобно и слишком технически сложно.

Теперь процесс выглядит привычно:

```text
выбрать файл
        ↓
загрузить изображение
        ↓
увидеть предпросмотр
        ↓
сохранить публикацию
```

Одно главное изображение автоматически используется сразу в двух местах:

```text
карточка публикации в карусели
                +
крупное изображение на странице публикации
```

Повторно загружать один и тот же файл для развёрнутой новости не требуется.

При удалении изображения публикация не удаляется и не ломается. Она просто корректно отображается без фотографии, а вся карусель продолжает работать.

1. Создать отдельное безопасное хранилище изображений публикаций.
2. Запретить выполнение серверных скриптов внутри каталога загрузок.
3. Реализовать серверный обработчик загрузки изображений.
4. Ограничить допустимые форматы и размер файла.
5. Добавить в редактор выбор изображения, загрузку, удаление и предпросмотр.
6. Автоматически заполнять поле `image_path` после успешной загрузки.
7. Сохранить путь к файлу в таблице `home_feed_items`.
8. Подключить одно и то же изображение к карточке карусели и развёрнутой публикации.
9. Проверить замену и удаление изображения.
10. Убедиться, что публикация без изображения не нарушает работу страницы и карусели.
11. Подготовить дальнейшее развитие редактора: панель форматирования, медиатеку и метаданные изображений.

# 1. Создание каталога изображений

Для файлов публикаций создан отдельный каталог:

```text
/docs/new-home/uploads/publications/
```

Внутри него изображения раскладываются по годам и месяцам:

```text
/uploads/publications/2026/08/
/uploads/publications/2026/09/
/uploads/publications/2027/01/
```

Такое устройство лучше одного общего каталога, потому что:

- в одной папке не накапливаются тысячи файлов;
- проще находить изображения по времени загрузки;
- проще создавать резервные копии;
- структура остаётся понятной при переносе сайта на другой сервер.

Серверные права каталогов установлены так, чтобы веб-сервер мог сохранять изображения, но сами папки не получали избыточных разрешений.


# 2. Защита каталога загрузок

В каталоге публикаций создан файл:

```text
/uploads/publications/.htaccess
```

Он запрещает обработку потенциально опасных серверных файлов:

```apache
RemoveHandler .php .phtml .php3 .php4 .php5 .php7 .php8 .phar .cgi .pl .py .sh
RemoveType .php .phtml .php3 .php4 .php5 .php7 .php8 .phar .cgi .pl .py .sh

<FilesMatch "\.(php|phtml|php3|php4|php5|php7|php8|phar|cgi|pl|py|sh|shtml)$">
    Require all denied
</FilesMatch>
```

Простыми словами:

```text
в каталог можно сохранить изображение
        ↓
но нельзя загрузить туда PHP-файл
        ↓
и заставить сервер выполнить его как программу
```

Это важная часть безопасности любой системы загрузки пользовательских файлов.


# 3. Серверный обработчик загрузки

Создан новый файл:

```text
/docs/new-home/admin/publication-image-upload.php
```

Он принимает изображение из административной панели и выполняет последовательную проверку.

## Проверяется метод запроса

Обработчик принимает только:

```text
POST
```

Прямой вызов другим способом не используется для загрузки файла.

## Проверяется CSRF-токен

Загрузка связана с действующей административной сессией. Это не позволяет сторонней странице незаметно отправить файл от имени авторизованного редактора.

## Проверяется размер

Максимальный размер файла:

```text
8 МБ
```

## Проверяется реальный MIME-тип

Разрешены:

```text
JPEG
PNG
WebP
```

Проверяется не только расширение имени. Сервер определяет фактический тип содержимого файла.

## Проверяется, что файл является изображением

Дополнительно используется проверка параметров изображения. Это защищает от файла, который только переименован в `.jpg`, но фактически изображением не является.

## Ограничиваются размеры изображения

Максимальная сторона изображения:

```text
12 000 пикселей
```

Это предотвращает загрузку чрезмерно больших файлов, способных создать лишнюю нагрузку на сервер.


# 4. Безопасные имена файлов

Исходное имя файла не используется как серверное имя напрямую.

Вместо него создаётся уникальное имя из времени и случайной последовательности. Пример структуры:

```text
/uploads/publications/2026/08/20260806-184530-a1b2c3d4e5f6.jpg
```

Такой подход решает сразу несколько проблем:

- одинаковые исходные имена не перезаписывают друг друга;
- кириллица и пробелы не создают проблем в URL;
- пользователь не может самостоятельно задать путь к системному файлу;
- имя сложно случайно угадать;
- структура остаётся пригодной для резервного копирования.

После сохранения файл получает обычные права чтения веб-сервером без разрешения на выполнение.


# 5. Новый блок в редакторе публикации

В правой колонке редактора создана отдельная карточка:

```text
МЕДИА
Главное изображение
```

Она содержит:

```text
предпросмотр текущего изображения
выбор нового файла
кнопку загрузки
кнопку удаления изображения из публикации
сообщение о результате операции
поле с автоматически сформированным путём
```

Блок визуально отделён от карточки «Публикация», поэтому правая колонка теперь имеет понятную структуру:

```text
Публикация
        ↓
статус, сохранение, корзина

Главное изображение
        ↓
файл, предпросмотр, загрузка, удаление
```


# 6. Как работает загрузка в интерфейсе

Редактор выбирает файл через стандартное поле браузера.

После выбора становится доступна кнопка:

```text
Загрузить изображение
```

JavaScript отправляет файл в:

```text
publication-image-upload.php
```

без перезагрузки всей страницы.

После успешной загрузки сервер возвращает JSON с публичным путём к файлу. Например:

```json
{
    "success": true,
    "path": "/new-home/uploads/publications/2026/08/example.jpg"
}
```

Далее редактор автоматически:

1. записывает путь в поле `image_path`;
2. показывает новое изображение;
3. выводит сообщение об успешной загрузке;
4. оставляет публикацию открытой для дальнейшего редактирования.

Загрузка файла и сохранение самой публикации являются двумя понятными действиями:

```text
изображение загружено на сервер
        ↓
путь появился в редакторе
        ↓
нажимаем «Сохранить»
        ↓
путь фиксируется в базе данных
```


# 7. Предпросмотр изображения

Предпросмотр обновляется автоматически при изменении `image_path`.

Логика:

```text
путь заполнен
        ↓
показываем изображение

путь пуст
        ↓
скрываем область предпросмотра
```

При повторном открытии публикации сохранённое изображение сразу отображается в редакторе.

Это позволяет визуально проверить, какая именно фотография привязана к материалу, не открывая публичную страницу.


# 8. Удаление изображения из публикации

Кнопка:

```text
Убрать изображение
```

не удаляет саму публикацию и не затрагивает другие материалы.

Она:

- очищает поле `image_path`;
- скрывает предпросмотр;
- сообщает, что изменение нужно сохранить.

После нажатия общей кнопки «Сохранить» публикация остаётся в базе, но больше не связана с изображением.

На текущем этапе сам физический файл может оставаться в каталоге. Это безопаснее, чем немедленное удаление, поскольку один файл в будущем может использоваться несколькими материалами. Управление неиспользуемыми файлами будет вынесено в будущую медиатеку.


# 9. Подключение изображения к публичной части

Главное изображение хранится в одном поле:

```text
home_feed_items.image_path
```

И используется повторно в нескольких представлениях.

## На главной странице

Изображение выводится в карточке публикации внутри новостной карусели:

```text
изображение
дата
заголовок
краткое описание
```

## На странице публикации

То же изображение выводится крупно:

```text
дата
заголовок
главное изображение
полный текст
```

То есть редактор загружает файл только один раз.

```text
одно изображение
        ↓
один путь в базе
        ↓
карточка + развёрнутая публикация
```


# 10. Проверка публикации без изображения

Отдельно проверен сценарий, когда `image_path` очищен.

Результат:

- публикация корректно исчезает из изображения карточки либо отображается по предусмотренной логике без него;
- вся карусель продолжает работать;
- соседние карточки не смещаются критически;
- переходы между публикациями сохраняются;
- развёрнутая страница открывается;
- текст и правая колонка остаются доступными;
- ошибок PHP и JavaScript не возникает.

Это подтверждает, что изображение является дополнительным элементом публикации, а не обязательным условием её существования.

# 17. Редактор метаданных изображения

Каждое изображение в будущей медиатеке должно получить собственную карточку редактирования.

Планируемые поля:

```text
alt
annotation
caption
credit
source_url
original_filename
title
```

## `alt`

Альтернативное текстовое описание изображения для доступности и случаев, когда файл не загрузился.

Пример:

```text
Читательница выбирает книгу у стеллажа библиотеки
```

## `annotation`

Внутренняя редакционная аннотация: что изображено, почему файл был загружен и где его предполагается использовать.

## `caption`

Подпись, которую можно выводить непосредственно под фотографией на публичной странице.

## `credit`

Автор фотографии, правообладатель или организация, предоставившая изображение.

## `source_url`

Ссылка на источник, когда это требуется правилами использования материала.

Эти данные не следует хранить только внутри HTML публикации. Для полноценной медиатеки лучше создать отдельную таблицу, связанную с файлами.

Возможная будущая структура:

```text
media_items
├── id
├── file_path
├── original_filename
├── mime_type
├── file_size
├── width
├── height
├── alt_text
├── annotation
├── caption
├── credit
├── source_url
├── created_at
└── updated_at
```
