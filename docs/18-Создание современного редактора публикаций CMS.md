# Что было сделано — простыми словами

День 18 превратил систему публикаций из динамической публичной части сайта в полноценную редакционную платформу.

До этого момента новости, анонсы и международные события уже выводились из таблицы `home_feed_items`, но добавление и изменение записей всё ещё во многом зависело от прямой работы с MySQL и phpMyAdmin.

Поэтому внутри проекта был создан новый административный раздел:

```text
/docs/new-home/admin/
```

Теперь новый интерфейс обеспечивает:

```text
защищённый вход администратора
        ↓
панель с общей статистикой
        ↓

        ↓
поиск и фильтрацию
        ↓
современную форму создания и редактирования
        ↓
безопасное сохранение в MySQL
        ↓
мягкое удаление в корзину
        ↓
восстановление из корзины
        ↓
защиту неопубликованных и удалённых страниц
```

Результат уже не является макетом. Редактор действительно создаёт записи, повторно загружает их по ID, изменяет данные, перемещает материалы в корзину, восстанавливает их и не позволяет неопубликованным публикациям открываться в публичной части.

# 1. Создание отдельного административного модуля

Новый редактор был размещён в изолированной папке:

```text
/docs/new-home/admin/
```

Такое разделение важно, потому что публичная часть и административный интерфейс теперь выполняют разные задачи:

```text
/new-home/
        ↓
публичный сайт для посетителей

/new-home/admin/
        ↓
закрытый редакционный интерфейс
```

Для административного модуля были подготовлены собственные:

```text
PHP-страницы
общий bootstrap
авторизация
подключение к MySQL
компоненты макета
CSS
JavaScript
```

Это позволило модернизировать редакционную работу без замены существующей структуры базы данных и без вмешательства в рабочую публичную часть сайта.

# 2. Bootstrap, авторизация и слой базы данных

Общая серверная основа была разделена на файлы:

```text
/docs/new-home/admin/includes/admin-bootstrap.php
/docs/new-home/admin/includes/admin-auth.php
/docs/new-home/admin/includes/admin-db.php
/docs/new-home/admin/includes/admin-layout.php
```

`admin-bootstrap.php` подключает функции, необходимые всем страницам редактора.

Слой авторизации закрывает административный раздел от публичного доступа. Для работы используется необходимая техническая cookie административной сессии, а не рекламная или аналитическая cookie.

Слой базы данных предоставляет единое контролируемое подключение к той же MySQL, которую уже использует публичный сайт.

Архитектура теперь работает так:

```text
запрос административной страницы
        ↓
admin-bootstrap.php
        ↓
проверка авторизации
        ↓
сессия и CSRF-защита
        ↓
admin-db.php
        ↓
подготовленная операция MySQL
```

Публичные формы регистрации, аналитические счётчики, рекламные cookies и сбор персональных данных посетителей не добавлялись.

# 6. Диагностика проблемы с CSS

Во время разработки общий `admin.css` загружался, но новые стили таблицы не применялись.

Проверка показала:

```text
admin.css подключён
        ↓
старые селекторы присутствуют
        ↓
новых селекторов в серверной копии нет
```

Для диагностики временно было добавлено правило:

```css
.admin-publications-table-wrapper {
    outline: 4px solid green !important;
}
```

Зелёная рамка доказала, что редактируется правильный файл и используется правильный селектор.

После этого основной блок CSS был вставлен именно в проверенную серверную копию, а версия файла в `admin-layout.php` была увеличена.

Так удалось избежать ненужного изменения PHP и точно определить причину: новый CSS-блок ранее не был сохранён в активном файле.

```text
/docs/new-home/admin/publication-save.php
```

```text
заполненная форма
        ↓

        ↓

        ↓

        ↓

        ↓
```

```text
редактор
        ↓
MySQL
        ↓
редактор
```

# 12. Мягкое удаление в корзину

Обработчик действий реализован в:

```text
/docs/new-home/admin/publication-action.php
```

Кнопка «Переместить в корзину» отправляет POST-запрос с данными:

```text
id
csrf_token
action = trash
```

SQL-операция остаётся обратимой:

```sql
UPDATE home_feed_items
SET
    is_published = 0,
    deleted_at = NOW()
WHERE id = ?
  AND deleted_at IS NULL
LIMIT 1
```

Строка физически не удаляется из MySQL.

Цепочка:

```text
публикация
        ↓
окно подтверждения
        ↓
снятие с публичного доступа
        ↓
заполнение deleted_at
        ↓
появление в корзине
```

JavaScript-подтверждение защищает от случайного нажатия.

# 13. Восстановление из корзины

Для записей в корзине показывается предупреждение и кнопка:

```text
Восстановить из корзины
```

Восстановление выполняет:

```sql
UPDATE home_feed_items
SET
    deleted_at = NULL,
    is_published = 0
WHERE id = ?
  AND deleted_at IS NOT NULL
LIMIT 1
```

Восстановленная запись намеренно остаётся неопубликованной.

Это защищает от автоматического появления на сайте старого или незавершённого материала.

Полный жизненный цикл теперь работает так:

```text
создание
        ↓
редактирование
        ↓
корзина
        ↓
восстановление
        ↓
неопубликованная редакционная запись
```

После восстановления материал снова появился в общем списке, а все его данные сохранились.

# 14. Защита публичных страниц

Публичный шаблон уже выбирал записи по `slug`, `locale` и разрешённому типу.

В SQL были подтверждены окончательные ограничения:

```sql
AND is_published = 1
AND deleted_at IS NULL
```

Теперь действует правило:

```text
опубликовано и не удалено
        ↓
страница доступна публично

не опубликовано
        ↓
возвращается 404

находится в корзине
        ↓
возвращается 404
```

Тестовый адрес:

```text
/new-home/ru/news/test-novogo-redaktora
```

перестал показывать неопубликованную запись.

В административном редакторе запись при этом осталась доступна.

# 15. Создание фирменной страницы 404

Изначально посетитель видел только:

```text
Новость не найдена.
```

Был создан локализованный шаблон:

```text
/docs/new-home/includes/publication-not-found.php
```

`news.php` сохраняет настоящий HTTP-статус:

```php
http_response_code(404);
```

и подключает фирменную страницу.

Новая страница содержит:

```text
метку ошибки 404
понятное объяснение
переход ко всем новостям
возврат на главную
адаптивную компоновку
русскую и венгерскую версии текста
```

Также передаётся:

```html
<meta name="robots" content="noindex, nofollow">
```

Первая попытка подключения завершилась ошибкой, потому что файл отсутствовал в ожидаемой папке `/new-home/includes/`. После размещения файла по точному адресу страница загрузилась, а обе ссылки были проверены и работают.

# 16. Персональные данные и нормативная область

Редактор не добавляет публичного сбора персональных данных.

В текущий объём не входят:

```text
регистрационные формы
формы обратной связи
личные кабинеты посетителей
рекламные трекеры
аналитические cookies
хранение персональных данных посетителей
```

Единственная необходимая cookie — техническая cookie административной сессии, используемая для авторизации и CSRF-защиты.

Редактор хранит только редакционные данные, предназначенные для сайта:

```text
тексты
метаданные публикаций
существующие пути к изображениям
статусы
SEO-поля
информацию о мероприятиях
```

Для самого создания внутреннего CMS-модуля внешнее предварительное согласование не требуется. Перед переходом в рабочий режим внутреннее одобрение организации остаётся административным вопросом, а не технической зависимостью редактора.

- кнопки форматирования вставляют контролируемую HTML-разметку.

## Операции базы данных

- новые записи добавляются;
- существующие записи загружаются и обновляются;
- мягкое удаление заполняет `deleted_at` и снимает публикацию;
- восстановление очищает `deleted_at` и оставляет запись неопубликованной;
- используются подготовленные запросы и CSRF-токены.

## Публичная безопасность

- неопубликованные записи не открываются публично;
- записи из корзины не открываются публично;
- опубликованные материалы продолжают работать;
- отсутствующая публикация возвращает фирменную страницу HTTP 404;
- ссылки страницы 404 проверены.


